# On Record data model

The D1 schema lives in `db/schema.ts`; its initial migration is `drizzle/0000_futuristic_rawhide_kid.sql`, the source-authentication/publication-guard migration is `drizzle/0001_careful_justin_hammer.sql`, the additive assessment migration is `drizzle/0002_calm_quentin_quire.sql`, and bilateral search-log migration is `drizzle/0003_first_thunderbolt_ross.sql`. String IDs are assigned by the application. All timestamp integers are Unix milliseconds. Application code obtains the Cloudflare D1 Drizzle handle with `getDb()` from `db/index.ts`.

| Concept | Tables | Relationship |
| --- | --- | --- |
| Speaker and original communication | `people`, `source_communications`, `source_captures` | A person has communications; each communication has numbered, immutable captured revisions and original text, transcript, content hash, capture time, and metadata. |
| Source authentication | `source_authentications` | A reviewer attests to an actual captured revision, recording reviewed URL and matching content digest, method, notes, and verification time. Each attestation is immutable. Intake metadata alone does not establish authentication. |
| Literal and normalized claim | `representations`, `propositions`, `proposition_relations` | A representation quotes one captured revision. Approved representations may refer to a shared proposition. Proposition relations retain explicit rationale for equivalence, supersession, contradiction, or topical relation. |
| Materiality and governing rules | `methodology_versions`, `materiality_decisions` | A representation receives one locked materiality decision tied to a methodology version before evidence search begins. Critical, Major, Supporting, and Not Material are stored as tiers; weighting and aggregate gates remain outside this schema. |
| Bilateral searches | `evidence_searches` | Each supporting or contrary search records its strategy, findings (including none), reviewer, and actual search time after materiality lock. Appending stops after adjudication. Both sides must be logged before assessment. |
| Reusable evidence | `evidence_objects`, `proposition_evidence` | A captured evidence source can bear a supporting, contrary, or contextual applicability judgment for several propositions. Effective dates and jurisdiction prevent accidental timeless reuse. |
| Finding and public history | `adjudications`, `adjudication_evidence`, `reviews`, `publications`, `corrections` | Each adjudication revision names its representation, proposition, materiality lock, methodology, considered evidence, search logs, and evidence cutoff. Approved review precedes publication. Corrections link original and optional replacement publication. |
| Candidate multidimensional assessment | `scoring_proposals` | Immutable revisions hold Accuracy and Context Integrity anchors and four Evidence Confidence factors: Authority, Evidentiary Sufficiency/Corroboration, Directness, and Temporal/Methodological Fit. These proposals cannot themselves be published as verdicts. |

`CHECKING` requires a null score. The initial migration's legacy `RATED` constraint allows only 100, 85, 65, 35, 15, or 0 and its legacy materiality names are CRITICAL/MAJOR/SUPPORTING/NOT_MATERIAL. **These are not the finalized VC005/VC006 instrument.** The additive `scoring_proposals` table records provisional Accuracy 100/95/85/65/35/15/0/U, Context Integrity 100/85/60/30/0/N/A, and the four separate Evidence Confidence factors (0–25 each). It requires a matching approved representation, authenticated source before materiality lock, non-M0 materiality, and an assessment timestamp after both supporting and contrary evidence searches. It precedes adjudication in the editorial workflow. At the API boundary the legacy storage tiers map to finalized M0=NOT_MATERIAL (weight 0), M1=SUPPORTING (0.75), M2=MAJOR (1), M3=CRITICAL (1.25); do not interpret the legacy tier labels as a revised standard. A later schema transition must replace the old `adjudications` constraints before publishable scored findings are possible. The SQL migrations check that materiality is locked strictly before evidence search starts and verify proposition references. The second migration checks source-authentication URL, digest, and capture time at insertion, then gates publication on a matching attestation made before materiality lock, approved representation, materiality lock, documented bilateral searches, the current adjudication revision, and the latest human review approving the adjudication after its creation. Considered evidence cannot be appended after review begins. A documented search can have found no evidence on one side. **Numerical verdict publication is disabled** pending the full schema transition and approved evidence sufficiency rules. The migrations block changes to captured source revisions, attestations, locked materiality, adjudications, reviews, publications, corrections, and scoring proposals. To revise a finding, append a new adjudication and publication; to correct a public record, append a correction.

Only representations can change from candidate to approved before materiality is locked. The application must use transactions for a complete workflow, authentication and authorization for editorial access, and independent reviewer policy; the schema does not decide who may review, whether evidence is adequate, or which claims are eligible for aggregate scoring. Aggregate politician scores are deliberately absent pending founder approved coverage thresholds.

Example insertion order: person → source communication → source capture → source authentication → proposition → representation (approve) → methodology version → materiality lock → both evidence-search logs → evidence object → proposition evidence → scoring proposal → adjudication → considered evidence → review → publication. An unresolved `CHECKING` finding may have no evidence links, with its bilateral search state documented in the adjudication. Do not publish seeded demonstration data as verified reporting.
